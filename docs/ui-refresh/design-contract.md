# Sprout native design contract

Status: **approved target; Android Home and Activity implemented, iOS full-app acceptance pending**, updated 2026-11-09 (America/New_York). This contract specifies presentation and interaction for the current SwiftUI and Jetpack Compose apps. It does not implement a finance feature or prove full-app runtime behavior. The [brief](brief.md) and [audit](audit.md) are the evidence baseline. The four root `sprout-*.png` images are visual references with unknown provenance, not native captures or approved component definitions.

## Thesis, hierarchy, and architecture

**Visual thesis:** quiet financial clarity: warm neutral canvas, deep green orientation, restrained emphasis, and numerals that are readable before decoration. **Content plan:** scope and freshness, one primary money figure or task, a scannable list, then relevant detail and action. **Interaction thesis:** selection moves to a clear destination; filtering updates the same context; status motion acknowledges an actual data event.

Keep iOS `SproutApp → RootView → AuthenticationView/MainTabView`, `Tab` identity, deep links, auth, SwiftData, network and service ownership. Keep Android `MainActivity → SproutApp → AuthNavigation/MainAppContent`, ViewModel/StateFlow, Room/Retrofit/WorkManager and Plaid callbacks. Native visual components receive display state and callbacks. They do not calculate balances, infer subscriptions, cancel services, persist settings, or own route state. No HTML/web import is a native design-system implementation.

- A money view starts with **what**, **account/period scope**, and **as-of freshness**. Show one dominant amount per viewport; do not give net worth, spend, savings, and recurring cost equal visual weight. A chart follows its labeled number and can be removed without losing the fact.
- Compact-screen gutters: 20 pt/dp (16 below 360 width). Related controls: 12 apart; label/value: 8; sections: 24. Rows share one surface and dividers. A distinct summary or action may use a card; routine lists do not need one card per item. Target 3–5 useful rows below navigation/summary on a standard phone at default text size.
- Screen title 28–32 pt/sp; section heading 18–20; row label 16; secondary 14–15; metadata at least 12 and never the only status cue. Summary amount 32–40; row amount 16–18. These are base sizes, not fixed rendered sizes. Long names wrap; amounts never silently clip.
- One primary action per view or sheet. Keep essential actions clear of safe areas, keyboard, and bottom navigation. Content scrolls when enlarged text needs room.

## Semantic foundations

These reference values are proposed for native review. The current iOS asset green is the brand seed, not a foreground color on every surface. Financial direction uses a sign and label; green/red represent state only when the state warrants them.

| Role | Light | Dark | Job |
| --- | --- | --- | --- |
| `canvas` | `#F6F8F4` | `#101B16` | Screen background |
| `surface` | `#FFFFFF` | `#17241D` | Action, summary, modal |
| `surfaceSubtle` | `#EBF2EA` | `#22332A` | Selection, quiet grouping, skeleton |
| `textPrimary` | `#16271D` | `#F0F6EF` | Titles, amounts, essential labels |
| `textSecondary` | `#526258` | `#B9CCBC` | Dates, scope, source, helper |
| `separator` | `#D7E2D7` | `#35493B` | Dividers and field boundaries |
| `action` / `onAction` | `#1C6A3D` / `#FFFFFF` | `#8BDD9D` / `#101B16` | Primary action and selected navigation |
| `actionSubtle` | `#D8ECDD` | `#234532` | Selection without success claim |
| `success` | `#227047` | `#8BDD9D` | Confirmed completion |
| `warning` | `#8B5B11` | `#F1C77A` | Review needed or stale data |
| `error` | `#A93830` | `#FFB4AC` | Failed operation or invalid field |
| `info` | `#245C7B` | `#9DD5F1` | Neutral explanation or active sync |

Calculated sRGB contrast for proposed primary/secondary text on canvas and action/status on surface exceeds 4.5:1; verify composited colors, disabled controls, and pressed states in native captures. State is always text plus optional icon, never color alone. `unknown`, `offline`, `stale`, and `failed` are separate meanings.

- **Type and financial numerals:** SF system text on iOS, Roboto/Material system text on Android; no new font dependency. Use native text styles and semibold sparingly. Align amounts with tabular/monospaced digits. Format currency and dates with locale, currency code for ambiguous or mixed currencies, and source precision. Never abbreviate a value in a detail or confirmation; accessible summary reads the full value. A true minus sign is not a debit/credit definition. Current `Double` storage is a separate data concern, not permission to round silently.
- **Spacing, shape, surface:** base scale 4/8/12/16/20/24/32 pt or dp. List row at least 56; form control at least 48; hit area at least 44×44 pt iOS or 48×48 dp Android. Radius 12–16 for actionable controls, 20–24 for one featured summary or sheet. Use a divider before shadow; shadows only clarify a floating layer. Avoid nested pills and decorative gradient behind routine UI.
- **Icons:** retain existing Sprout app icon and green cue. Use SF Symbols on iOS, Material vector icons on Android for the same *meaning*. Verified merchant logos require provenance and a text label; otherwise a neutral monogram/category icon. Avoid emoji in fields and status rows.
- **Charts:** show measure, currency/units, account scope, start/end dates, comparison basis, and missing-data treatment. Time series use ordered lines; intervals use bars. Do not interpolate absent samples or invent trends. Provide a text summary and accessible points/table; differentiate series by label/shape as well as color. Omit chart when no trustworthy series exists.
- **Motion:** 120–240 ms for selection and state transitions. Use a brief native sheet transition; no bouncing money actions, autonomous floating circles, forced splash wait, or animated numbers that imply changed data. Respect Reduce Motion/Remove Animations. Use system progress with a static label; success haptic only after confirmed outcome.

The platform touch targets and adaptive navigation choices follow [Apple accessibility guidance](https://developer.apple.com/design/human-interface-guidelines/accessibility), [Android Compose accessibility guidance](https://developer.android.com/codelabs/jetpack-compose-accessibility), and [Android Material 3 navigation guidance](https://developer.android.com/develop/ui/compose/designsystems/material3). Treat the exact palette and layout thresholds above as Sprout proposals to validate in native builds.

At enlarged text, rows may stack metadata and amount; filters may scroll horizontally with a spoken selected state; navigation may adapt. Essential content cannot rely on hover, color, motion, or a chart. Test the same fictional fixture across light/dark, text scale, reduced motion, screen reader, keyboard/IME, and narrow/expanded width.

## Native component contracts

These are semantic patterns implemented separately in SwiftUI and Compose, not a new cross-platform rendering framework.

| Component | Anatomy and variants | Behavior |
| --- | --- | --- |
| `AmountText` | Amount, currency, sign, optional period/basis and privacy mask; summary/row/detail/concealed | Locale-aware, aligned digits; no fake zero for unknown; mask keeps label and accessible privacy state. |
| `TransactionRow` | Merchant/description, category/date, amount, verified logo or neutral icon, optional source/sync state; income/expense/transfer/pending/syncFailed | Tap only with resolvable ID. Pending/failed/conflict describe sync, not bank settlement. Long names wrap; state stays explicit. |
| `SubscriptionRow` and detail | Merchant/service, amount/cadence, verified next date, evidence/status, relevant action; active/paused/cancelled/unknown | Inferred recurrence says “Possible recurring payment.” “Renews”/“cancelled” require source evidence. Separate merchant tracking from `SproutPlan` billing. Unsupported cancel/reminder stays absent or explained as unavailable. |
| `StatusTimeline` | Ordered event, timestamp/time zone, source, state, next step; complete/in progress/needs action/failed/unknown | Events come from an operation log/confirmation. Never fabricate a completed step; expose recovery and current step. |
| `GoalProgress` | Name, current/target, period, bar plus text, last update; on track/behind/complete/unavailable | Only with a defined goal contract. No percentage without target; clamp bar while stating actual value. |
| Buttons | Label, optional meaningful icon, enabled/busy; primary/secondary/quiet/destructive/link | One primary per context; busy blocks duplicate submit; destructive label names object/action; no success before readback. |
| Inputs | Persistent label, value, helper/units, inline error, focus/clear/reveal; text/email/password/currency/date/search | Correct keyboard/autofill; errors persist and are announced; currency input stores source precision; flexible height. |
| Filters | Search, period/account/type, result count/scope, selected state, clear; single/multi/date range | Preserve state across detail; scope appears above totals; active filter must change results. |
| Banners | Icon, title, consequence, one recovery; offline/stale/syncing/error/info | Persistent when financial truth is affected; age and recovery explicit. Toast only for low-stakes transient acknowledgement. |
| Empty/loading/error | Heading, reason/scope, next step; layout-preserving skeleton; retry; new account/no matches/not connected/partial/failed | New account is not $0. No matches differs from no records. No fixture number during loading; partial data labels missing scope. |

## Financial and action language

- Preserve source `income`, `expense`, `transfer`, `amount`, `currency`, `date`, `isRecurring`, and sync metadata. “Total spent” needs a period, eligible expense set, and coverage. “Net worth” needs verified assets and liabilities; the reference `$28,450.75` is not app data. “Up 8.2%” needs a real comparison window. Transfers are not spending or income.
- “Add expense” stays a manual expense action. “Connect bank account” requires a live, reachable Plaid flow. “View transaction” needs a resolvable record. “Retry sync” needs an actual retry operation. “Request sent”, “Pending”, “Completed”, and “Failed” reflect distinct acknowledgements; submission is not cancellation or payment completion.
- “Recurring payments” or “Possible recurring payments” describe merchant charges according to evidence. “Sprout plan”/“Sprout Premium” describe app billing. The current iOS `Cancel Subscription` is a no-op Sprout-plan mock; it cannot claim merchant cancellation. “Manage in App Store” names a destination, not an outcome. Android RevenueCat initialization is not a plan screen.
- “Reminders on”, “Notifications saved”, and delivery timing need persisted settings and permission; current iOS toggles only print on save. “Connected”, “Synced”, and “Updated at” require an event/timestamp; otherwise use “Status unavailable” or scoped “Last checked [time]”. Do not promise savings, eligibility, or guaranteed cancellation.
- Fictional fixture frames must carry **demo data** in review metadata. Product UI must not present demo numbers as a user's money. Details use full dates and source time zone; relative dates have an absolute accessible value.

## Representative frames for approval

These are **approval candidates**, not approved Figma frames or native evidence. Use one explicitly fictional fixture and record device, OS, theme, text scale, date/time, scope, and data provenance in every review frame. Root PNGs may guide composition but not claims or values.

1. **iOS + Android Home, light/dark:** labeled navigation, scope/freshness, one source-backed summary or honest new-account empty state, one useful action. No “net worth” without assets/liabilities.
2. **iOS + Android Activity → transaction detail:** search/filter, period/result count, income/expense/transfer and sync variants; detail has full amount/date/source and back restores filters.
3. **iOS + Android recurring payments → merchant detail:** inferred versus confirmed recurrence, cost/cadence/next date only when supported; unsupported cancellation explained. Separately show **Sprout plan** where billing evidence exists.
4. **iOS + Android sign-in/error and goal empty/progress:** native inline error/recovery and large text; goal percentage only with a valid target.

Composition and labels need approval before implementation. Native captures become acceptance evidence after the routes and safe fixture exist. Figma authoring, if approved and writable, remains a design artifact.
