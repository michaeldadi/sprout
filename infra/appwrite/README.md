# Sprout Appwrite infrastructure

One Terraform root manages any Sprout Appwrite environment. The selected
`environments/<name>.tfvars` file supplies project and resource IDs; the
Terraform workspace with the same name holds that environment's state. The
workspace guard fails a plan if the names differ. Add another environment by
adding one data file, without copying resource code.

The current files record the **existing** production and staging Appwrite Cloud
projects as read on 2026-11-09. The `import` blocks adopt those resource IDs
into state. They do not authorize replacement or creation. Both projects had
an empty TablesDB database at inventory time, a document bucket, and a landing
site. Production
also has five existing template functions and one Terraform project API key.
Function and site deployments generated by Appwrite from Git are runtime
artifacts; the Git linkage and build configuration are modeled here. Their
latest deployments were failing at inventory time, and this configuration does
not make them work.

## Use

1. Create an encrypted HCP Terraform remote backend configuration at
   `backend.hcl` using `backend.hcl.example`. The workspace prefix can be
   shared; each environment uses its own workspace. Authenticate to HCP
   Terraform without putting tokens in this repository.
2. Supply `APPWRITE_API_KEY` for the selected Appwrite project and
   `APPWRITE_ORGANIZATION_API_KEY` for project and key administration through a
   secret manager or local environment. Never commit either credential or a
   Terraform state file. The official provider cannot create a project API key:
   bootstrap a scoped key in Appwrite, then add and import its metadata.
   The staging key was bootstrapped on 2026-11-09 and its generated ID and
   28 scopes are recorded in `environments/staging.tfvars`.
3. Run `./tf.sh staging validate` or `./tf.sh production validate` for
   formatting and configuration syntax. This does not check live drift or
   environment values. Run `./tf.sh <environment> plan` to preview import and
   drift. It writes a private `.plans/<environment>.tfplan` containing sensitive
   values. Inspect the full plan and its SHA-256, then run
   `./tf.sh <environment> apply` to apply that saved plan. Delete the local plan
   after use. The first apply imports existing resources into that workspace's
   remote state.

The production Speech recognition function has a credential-shaped variable.
Its value is deliberately absent from committed configuration. Supply
`TF_VAR_function_secret_values` as a JSON map with key
`speech_huggingface_token` from a secret manager when planning production.
The provider's write-only `value_wo` field keeps the value out of state.
Several other template function variables are currently blank in Appwrite;
their blank configuration is recorded literally.

Mobile builds select their Appwrite project independently of Terraform state.
Set `SPROUT_APPWRITE_ENDPOINT` and `SPROUT_APPWRITE_PROJECT_ID` for the selected
environment. Android reads these public identifiers and
`SPROUT_GOOGLE_WEB_CLIENT_ID` from `apps/.env.local` at build time. iOS reads
the same three build settings through `Info.plist`; pass them through the
selected Xcode configuration or CI. The Google web client ID must be the
same value declared in `native_oauth.google.native_client_ids` for that
environment. Keep provider secrets out of mobile builds. Until the Appwrite
financial data path is in place, existing social auth UI remains fail-closed.

## Coverage and gates

The official `appwrite/appwrite` provider is pinned at 2.3.0. This root
defines the existing projects, TablesDB databases, storage buckets, sites and
site variables, production functions and variables, and the production
project API key. No TablesDB tables, rows, users, teams, messaging resources,
or webhooks existed in either project at inventory time. Appwrite-generated
deployment and preview domains are outputs of deployments, not custom domains.

Provider 2.3.0 does **not** model the existing iOS/Android platform
registrations, OAuth/auth method settings, or the bucket `stripMetadata`
setting. The `settings.tf` bridge declares and reads those settings during
every plan, then applies reviewed differences through Appwrite's API with a
readback. It never deletes remote resources. Production currently strips
document metadata; staging does not. Native Apple sign-in uses the exact
case-sensitive iOS bundle ID, while Google uses the current Android web OAuth
client ID as its Appwrite audience. Verify that web client in Google Cloud
and configure the same server client ID in the iOS build before activating
Google sign-in.

The landing sites point to `./apps/web`, which is absent from this checkout.
The existing site and function deployments were not imported. The optional
manual-transactions function below has its own code-defined deployment.

On 2026-11-09, the staging Terraform project key was bootstrapped in Appwrite.
Seven existing staging resources were imported into the `sprout-appwrite-staging`
HCP state: the project, project key, TablesDB database, site, and three site
variables. The subsequent apply recorded 56 Terraform tracking entries,
hydrated the site and public variable resources, and corrected the iOS
platform bundle ID and Apple/Google native client IDs. The OAuth providers
remain disabled. Concurrent Apple and Google PATCH requests initially caused
Apple's readback to fail; a serial recovery apply completed, and a fresh
`terraform plan -detailed-exitcode` returned 0 (no changes). `tf.sh apply`
now uses `-parallelism=1` to avoid this race. Both temporary four-scope
organization keys were revoked and their local secrets and plan files removed.

On 2026-11-09, 27 existing production resources were imported into the
`sprout-appwrite-production` HCP state: the project, existing 85-scope key,
TablesDB database, site and three site variables, five functions, and 15
function variables. A separate state readback found all 27 managed IDs and 55
settings data-source observations; the imported Hugging Face variable's secret
value was absent from state. This was a state-only import: no production plan
was applied. The temporary 28-scope
project key was deleted, both temporary four-scope organization keys were
revoked, and their local secrets were removed. The existing production key
remains untouched; its secret is unavailable locally. A full production plan
still requires that key or another scoped project credential and the production
function secret supplied outside source control. It also needs a fresh review
before any production apply.

OAuth refuses to mint an organization key that outlives its grant. The Sprout
Finance console did not show the documented Partners key section, so future
local plans need a newly minted short-lived organization key or another
supported organization credential. If the local Python 3.13 Appwrite settings
bridge reports `Missing Authority Key Identifier` under the machine's managed
CA bundle, use `/usr/bin/python3` for the bridge after verifying its TLS
connection. Do not disable certificate verification.

## First financial slice: manual transactions

`manual_transactions_enabled` opts an environment into the same Terraform
resources; it is true only in `staging.tfvars` today. The slice defines a
private `manual_transactions_v1` table, its columns and owner/modified index,
and a TypeScript function built from a pinned package lockfile. Production has
not been changed. The iOS SwiftData and Android Room models still store amounts
as `Double`, so the clients must be migrated before they write this table.

The table uses a stable client-generated row ID for idempotent retries; an
authenticated owner ID; a signed integer amount in the currency's minor unit
and ISO currency code;
type, category, description, merchant, and transaction date; source and source
ID; server version, modified timestamp, and deletion marker. Keep Plaid-linked
accounts, recurring-charge detection, budgets, and goals out of this first
schema until their source and reconciliation rules are specified. Define an
explicit conversion for existing local data and migrate both local models
before Appwrite sync, avoiding a direct binary floating-point conversion into
a remote financial value.

The table has row security with no broad table read, update, or delete grant.
The server function derives the owner from a verified Appwrite session, sets the
row's user-specific permissions, validates money and currency, and enforces
version checks and tombstones. The client must not provide the authoritative
owner or bypass the function with a project API key. The function validates
JavaScript-safe integer amounts and signed 32-bit versions because Appwrite
returned full signed 64-bit bounds for the integer columns despite narrower
create requests; provider 2.3.0 rejected that readback.

The first staging apply on 2026-11-09 stopped after creating the private table,
all 15 columns, and the index. The Appwrite provider rejected its own readback
of integer bounds, and the existing 28-scope staging Terraform key could not
grant the function's `rows.read` and `rows.write` scopes. The bounds in this
configuration now match Appwrite's readback. The function, its two nonsecret
variables, and its first deployment were created through the connected
Appwrite API from the same reviewed Terraform configuration and TypeScript
archive, then imported into the staging HCP Terraform state. Import did not
hydrate the deployment's source fields, so a reviewed Terraform plan replaced
that deployment using create-before-destroy. The active deployment is
`6af1b8bc084346968a89` and was independently read back as ready. The
post-apply staging plan returned **no changes**. The temporary organization
key used for reconciliation was revoked and removed from Keychain; the
original 28-scope project key remains.

Local checks passed four focused TypeScript tests, the function build, and
Terraform validation. A live unauthenticated execution returned HTTP 401 with
`unauthorized`. With specific authorization, a live staging test on 2026-11-09
created two fictional email/password users and one transaction row. The active
function returned 201 for the owner's create, 200 for its replay, 404 for the
other user's get and delete, an empty list for the other user, and the row for
the owner. The owner's update and replay returned version 2; a stale-version
update returned 409. The owner's delete and replay returned version 3 with a
deletion marker. The single-row list returned no next cursor. The test row and
both accounts were then deleted; an independent readback found zero rows and
404 for both users. This did not simulate a lost network response or exercise
two simultaneous edits, a second pagination page, or two-device restore.
Those cases need live validation before enabling mobile writes. Production
needs a separate reviewed plan and data-migration decision. See [TablesDB Terraform resources](https://appwrite.io/docs/tooling/terraform/resources/databases)
and [Appwrite permissions](https://appwrite.io/docs/advanced/security/permissions).
